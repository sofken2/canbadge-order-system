# packages/e2e（通し確認・負荷テスト）

api と print-worker を、本番と同じように別々のプロセスで起動して、動きを確かめる。`bun run test` に含まれる。

| パス | 内容 |
| --- | --- |
| `src/flow.test.ts` | 通し確認（T09）。注文 → 支払い → 印刷 → 印刷確認 → 組み立て → 完成 → 呼び出しモニター → 受け渡し |
| `src/processes.ts` | api と print-worker の起動（`startStack`）。一時的な DB・空いているポート |
| `src/load/` | **負荷テストの道具（Q04）**。下の説明 |

## 負荷テスト（Q04）

模擬の来場者と、模擬のスタッフ（レジ・印刷確認・組み立て・受け渡し・呼び出しモニター）が、**本物の API を、本物の画面と同じ順で呼んで**、注文から受け渡しまで進める。1 時間あたりに処理できる件数と、**どこが詰まるか**を測り、人数・設定・受付を止める目安を決める材料にする（Q04）。

```sh
cd packages/e2e
bun run load                                   # 既定：120 人・20 分・レジ 2・組み立て 3・受け渡し 1（実際は約 2 分）
bun run load --visitors 200 --assemblers 4 --out report.json
bun run load --help                            # 引数の一覧
```

既定では、一時的な DB で api と print-worker を起動する（本番のデータには、触れない）。終わると、結果を端末に出し、`--out` で JSON も書き出す。**整合性の確認が 1 つでも崩れる、または作業が失敗したら、終了コード 1**。

### 見かた

| 項目 | 何がわかるか |
| --- | --- |
| 件数 | 注文 → 支払い → 印刷確認 → 組み立て → 受け渡し。どの段階で、止まったか |
| 待ち時間（仮想） | 段階ごとの待ち（平均・中央値・95%・最大）。**いちばん長く待つ段階が、詰まっている所** |
| 稼働率・処理能力 | 担当ごとの、働いていた割合。90% 近いと、余裕がない。段階ごとの、1 時間の理論上の処理能力 |
| ピーク | 列・待ちの、最大の長さ |
| API の応答時間 | エンドポイントごとの p50・p95・p99・最大と、失敗（ステータスごと） |
| SSE | 同時の接続の数、エラー、操作から画面に届くまでの遅れ、取りこぼし |
| 整合性の確認 | 注文番号の重複・欠け、取りこぼし、状態のずれ、売上のずれ、印刷中が 2 枚、面付け数の超過、作業のエラー、SSE のエラー |
| 見直しのたたき台 | ボトルネック、1 人増やしたときの効果、**受付を止める（ビジー）目安**（未完成が何件を超えたら、待ちが約 10・20・30 分）、印刷を待つ時間の見直し |

### モデルの前提（結果を読むときの注意）

- **人の作業時間は、仮想の秒**（実際の運用での秒）で決め、`--speed` 倍の速さで進める。**サーバーへの負荷（リクエストの密度）は、その倍率だけ、濃くなる**。既定の 30 倍なら、実際の運用の約 30 倍のペースで、API を叩いている（ストレステストとして、安全側）
- 圧縮に合わせて、サーバー側の待ち（SSE の確認間隔 `SSE_POLL_MS`・印刷キューの巡回・印刷を待つ時間）も、同じ倍率で縮めて起動する。SSE の遅れの数字は、本番の 2 秒間隔より、短く出る。**本番の遅れは、おおよそ「確認間隔（2 秒）+ 数十 ms」**
- 作業時間の既定値（レジ 25 秒・組み立て 100 秒・受け渡し 20 秒・印刷 45 秒・確認 20 秒）は、**たたき台**。**実際のリハーサルで測った値に置き換える**と、結果が現実に近づく（`--cashier-service-seconds` など）。組み立ては、バッジマシンの手作業なので、ばらつきが大きい
- 来場者は、ばらばらに（指数分布の間隔で）来る。同じ `--seed` なら、同じ客・同じ作業時間で再現できる（変えて、何度か流すと、ばらつきがわかる）
- 来場者は、それぞれ別の端末・別の接続元（IP）として扱う（IP ごとの回数の制限・端末ごとの支払い待ちの上限に、全員が、1 人として数えられないように）
- スタッフ画面と同じ動き：「変わった」の通知（SSE）が来るたびに、一覧を取り直す（担当の数だけ、取り直しの負荷が増える）。組み立て係の取り合い（別の人が先に取った → 409）は、ふつうに起きることとして数える
- ネットワークの遅れ（学内の Wi-Fi・Cloudflare 経由）・スマホのカメラ・Caddy は、含まない（api と print-worker を、直接、叩く）
- **Turnstile は通さない**（一時的な api は、`TURNSTILE_SECRET_KEY` なしで起動する）

### 動いているサーバーに流す（`--target`）

`--target http://localhost:3002 --yes-write-to-target`。**テストの注文が、そのサーバーに残る**ので、**本番には流さない**（リハーサル専用の、空の環境で）。未完成の注文があるサーバーには、流さない（本物の注文が混ざるため）。スタッフ用の API を使うので、**処理 PC の中（localhost）から**でないと動かない（A05）。サーバー側の待ち（SSE・印刷）は、本番の値のままなので、`--speed 1` に近い値で流す。

### 作ったもの

`config.ts`（引数）・`sim.ts`（再現できる乱数・時間の圧縮・順番待ちの列）・`stats.ts`（集計）・`world.ts`（共有の状態・時間を測る fetch・SSE）・`actors.ts`（来場者とスタッフ）・`run.ts`（実行と、最終状態の読み取り）・`report.ts`（整合性の確認・助言・報告）・`main.ts`（入口）。計算の部分（`stats`・`sim`・`config`・`report`）は、テストで確かめている。小さな規模（10 人）で、実際に流すテストも、`bun run test` に含まれる。
