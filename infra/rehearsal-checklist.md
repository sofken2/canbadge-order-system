# 実機の確認表（Q02 通しテスト・Q03 回線断テスト）

本番と同じ環境（処理PC・プリンター・Cloudflare 経由・実際のスマホ）で、**ここで初めて組み合わさるもの**を確かめる。自動テスト（`bun run test`）は、api と print-worker を実際に起動して、注文から受け渡しまでを通しているが、**本番ドメイン・Access・Turnstile・実機のカメラ・実プリンター・学内ネットワーク**は含まない。ここが対象。

- **本番の数週間前までに行う**。見つかった問題を直す時間を残す
- 表の「結果」に、○・×・メモ（日時・端末・OS）を書く。×は、末尾の「見つかった問題」に足す
- 先に済ませておくもの：[processing-pc.md](processing-pc.md)（I01）・[cloudflare.md](cloudflare.md)（I03）・[backup.md](backup.md)（I04）・プリンターの較正（P03・Q01）
- 確認用の端末：**iPhone（Safari）と Android（Chrome）の両方**。来場者用は**モバイル回線**と**学内 Wi-Fi**の両方

## 2. Q03 回線断テスト

**運営の決定**：回線が切れているあいだは、**新しい注文を受け付けない**。すでにキューにある（支払い済み・支払い待ち）注文だけを、**処理PC の中**で処理して、必要なら**手動で**印刷する。会場 LAN からのスタッフ用（PIN 認証）は、優先度を下げた機能で、**未実装**（spec.md 2 章「優先度の変更」・14 章）。この表は、その運用が**今のシステムで回る**ことと、**意図して断られること**を、確かめる。

**切り方**：ルーターの**インターネット側（WAN）だけを抜く**（会場 LAN と処理PC・プリンターは生かす）。できなければ、処理PC のネットワークを切る（LAN の項目はスキップ）。

| --- | --- | --- | --- |

### 回線が切れたときの運用（決定）

スタッフ向けの、1 枚の手順にする。

1. **気づいたら**：処理PC のモニターと、レジ・印刷係に、声をかける
2. **新しい注文を止める**：処理PC の設定画面で、受付を**「ビジー」**にし、メッセージを入れる。**「終了」にしない**（支払い待ちの注文が、失効するため）
3. **すでにある注文を処理する**：レジ（注文番号の入力）・印刷確認・組み立て・受け渡しは、**処理PC の中だけ**で行う（スタッフ用の画面は、会場 LAN のスマホからは使えない）。呼び出しモニターは、そのまま続く
4. **手動で印刷する**：待たずに出したいとき、設定の「印刷を待つ最大の秒数」を **1** にして、出し終わったら、**元の値に戻す**
5. **来場者へ**：「回線の都合で、新しい注文を止めています。いまの注文は、順に出します」と、口頭か貼り紙で伝える。**紙での注文は、受け付けない**（回線が戻ってから、来場者に、もう一度、注文してもらう）
6. **戻ったら**：トンネルの再接続を確かめ、受付を**「受付中」**に戻す

**将来の改善（提案）**：手動の印刷は、設定の秒数を変える運用になっている。**「今すぐ印刷」のボタン**（待ち時間を無視して、いまある分で、1 枚つくる）があると、操作を間違えにくい。ただし、契約（`packages/shared` のエンドポイント）の変更になるので、**入れるなら、先に提案を出して、契約オーナーの確認を受ける**。

## 9. 本番の前に、データを片づける

テストで作った注文・画像・印刷の PDF が、本番の売上・注文番号に混ざらないようにする。

1. `bun run backup`（念のため、テストのデータを残す）
2. `stop-all.ps1`
3. データ置き場（`C:\canbadge\data\`）の `app.db`（`app.db-wal`・`app.db-shm` があれば、それも）・`images\`・`sheets\`・`print-out\` を、別の場所へ移す
4. `start-all.ps1`（空の DB が、自動で作られる）
5. **設定画面で、価格・上限・印刷を待つ時間を、入れ直す**（既定値に戻っている）
6. 営業開始は、本番の日の朝に押す（注文番号が、その日の 001 から始まる）
