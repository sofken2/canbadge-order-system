# バックアップと復旧（I04）

処理PC が故障しても、学祭を続けられるようにする。**DB と画像を、数分おきに、別の物理ドライブへ複製**し、予備機で復旧する。

## 何をバックアップするか

| 対象 | 方法 | 備考 |
| --- | --- | --- |
| `data\app.db`（注文・状態・操作ログ・設定） | SQLite の `VACUUM INTO` で、整合性のあるコピーを作る | 稼働中のファイルをそのままコピーすると、書き込み中に壊れることがあるため、使わない。コピーしたあと、`integrity_check` で検証してから完成にする |
| `data\images\`（来場者が作ったデザインの画像） | 増えた分だけコピー | 画像は ID の名前で、一度書かれたら変わらない。バックアップ側からは、何も消さない |

**バックアップに入らないもの**（再生成できる、または秘密情報）：

| もの | 扱い |
| --- | --- |
| `data\sheets\`・`data\print-out\`（印刷用の PDF） | DB と画像から作り直せる |
| `data\logs\` | 復旧には要らない |
| **`.env`**（Access・Turnstile のキー、`STAFF_HOST` など） | **秘密情報。別に保管する**（下の「別に保管するもの」） |
| `%USERPROFILE%\.cloudflared\`（トンネルの認証ファイル） | **秘密情報。別に保管する** |

## 置き場所の構成

```
<BACKUP_DIR>\
  snapshots\20261103-100500\app.db     5 分おきの、DB の複製（既定で 288 個＝24 時間分を残し、古いものから消す）
  images\<ID>.png ...                  画像（増えた分だけ足す。消さない）
  latest.json                          直近の成功の記録
```

DB は数 MB 程度なので、288 個でも小さい。ドライブの空き容量は `check-backup.ps1` で見られる。

## 1. 準備（本番の処理PC）

1. **バックアップ先を決める**：処理PC の内蔵ドライブとは**別の物理ドライブ**（USB メモリが前提。外付けの SSD でもよい）を、PC につなぐ。同じドライブでは、故障したときに一緒に失われる。**USB メモリは 2 本用意して、交代で使う**（次の 1-2 を参照）
2. `.env` に書く：
   ```
   BACKUP_DIR=E:\canbadge-backup
   # BACKUP_KEEP=288   （残すスナップショットの数。省略可）
   ```
3. 1 回、手で取って確かめる：
   ```powershell
   cd C:\canbadge\infra\windows
   .\run-backup.ps1
   .\check-backup.ps1
   ```
   `OK` が出て、`E:\canbadge-backup\snapshots\` にフォルダができれば成功。
4. 定期実行を登録する（**管理者の PowerShell**）：
   ```powershell
   cd C:\canbadge\infra\windows
   .\register-backup-task.ps1 -User canbadge
   ```
   5 分おきに、`canbadge` で実行される（`-Minutes 10` で間隔を変えられる）。結果は `data\logs\backup.log` に追記される。

## 1-2. USB メモリで運用するときの注意

バックアップ先は、USB メモリでよい（クラウドは使わない方針）。次の点を守る。

| 項目 | 内容 |
| --- | --- |
| 容量 | **16 GB 以上**。DB は数 MB、画像は 1 枚 1 MB 前後なので、数百個の注文でも 1 GB に届かない。余裕を見て選ぶ |
| 形式 | NTFS か exFAT（FAT32 は、1 ファイル 4 GB の上限がある） |
| ドライブ文字を固定する | USB メモリは、挿す口や順番で `E:`・`F:` と変わる。変わると、バックアップ先が見つからず失敗する。**ディスクの管理**（Windows キー + X → ディスクの管理）で、USB メモリのドライブ文字を `E:` などに固定し、`.env` の `BACKUP_DIR` と合わせる。**同じ口に挿し続ける** |
| 挿したままにする | 抜き差しの途中でバックアップが走っても、途中の状態は完成扱いにならない（`.partial`）ので、壊れたスナップショットは残らない。ただし、書き込み中に抜くと、そのスナップショットは無駄になる |
| **2 本用意して、交代で使う** | USB メモリは、突然壊れることがある。**1 本は処理PC に挿し、もう 1 本は別の場所（責任者の手元など）に置く**。半日〜1 日に 1 回、交代する（下の「交代のしかた」） |
| 暗号化（任意） | 紛失したときに、来場者の画像と注文の情報が見られないよう、**BitLocker To Go** で暗号化できる（Windows の Pro 以上）。パスワードは、PC とは別に保管する |

### 交代のしかた

1. `check-backup.ps1` が `OK` で、直近のバックアップが新しいことを確認する
2. タスクバーの「ハードウェアを安全に取り外す」で、USB メモリを取り外す（**バックアップが走っていない間に**。5 分おきなので、`run-backup.ps1` の直後がよい）
3. もう 1 本を、**同じ口**に挿す。ドライブ文字が `.env` と同じか確認する
4. 次のバックアップ（最長 5 分後）で、新しい USB メモリに、画像が全部コピーされ、最新のスナップショットが作られる（画像のコピーは、足りない分を足す仕組みなので、空の USB メモリでも自動で揃う）
5. `check-backup.ps1` が `OK` になることを確認する
6. 外した USB メモリは、**別の場所**に保管する。これが、PC が故障したときの復旧元になる

交代のあいだ（取り外してから、挿し直して次のバックアップが走るまで）は、バックアップが取れない時間になる。**交代は、混雑していない時間に、手早く行う**。

## 2. 当日の見回り

営業の開始前と、途中の見回りで、次を実行する。**15 分以上取れていないと、`NG` と理由が出る**。

```powershell
C:\canbadge\infra\windows\check-backup.ps1
```

| `NG` の内容 | 原因と対処 |
| --- | --- |
| バックアップ先が見つかりません | 外付けドライブが外れた、またはドライブ文字が変わった。つなぎ直す。変わっていたら `.env` の `BACKUP_DIR` を直す |
| 15 分以上、取れていません | `data\logs\backup.log` を見る。ドライブの空き容量不足、タスクが止まっている（タスクスケジューラの `canbadge-backup`）など |
| まだ 1 回も取れていません | 手順 3・4 が済んでいない |

## 3. 復旧（予備機で再開する）

処理PC が壊れたときの手順。**新しい PC に、同じ状態を作ってから、データを戻す**。

| # | 作業 | 参照 |
| --- | --- | --- |
| 1 | 専用ユーザー・ツール・リポジトリ・`.env`・電源設定・自動ログオン（まだ起動タスクは登録しない） | [processing-pc.md](processing-pc.md) の 1〜6 |
| 2 | バックアップ用のドライブを、予備機につなぐ | |
| 3 | 画面をビルドする：`cd C:\canbadge; bun run build` | |
| 4 | **データを戻す**（下の「復旧コマンド」） | |
| 5 | トンネルの認証ファイルを戻し、サービスにする | [processing-pc.md](processing-pc.md) の 7 |
| 6 | 起動タスクとバックアップのタスクを登録する | [processing-pc.md](processing-pc.md) の 8、この文書の 1 章の 4 |
| 7 | 再起動して、動作を確かめる（下の「確認」） | |

**故障した PC が、まだ動いているとき**：トンネルの接続が両方の PC に張られ、来場者が壊れかけた PC に振り分けられることがある。**故障した PC は、電源を落とすか、ネットワークから外す**。

### 復旧コマンド

`api` と `print-worker` が動いていない状態で、実行する（`stop-all.ps1` で止める）。

```powershell
cd C:\canbadge
bun run restore E:\canbadge-backup
```

- 完成している**最新の**スナップショットを使う。時点を選ぶときは、スナップショットのフォルダを指定する：
  `bun run restore E:\canbadge-backup\snapshots\20261103-100000`
- 復旧元の DB は、`integrity_check` で検証してから置く。壊れていれば、何も変えずに失敗する
- 復旧先（`data\`）にすでに DB があるときは、**止まる**。置き換えてよければ `--force` を付ける。今の DB（と、その WAL・SHM）は `data\before-restore-<時刻>\` に退避され、消されない
- 画像は、足りないものだけが戻る

### 確認

| # | 確認 | 結果 |
| --- | --- | --- |
| 1 | スタッフ画面（レジ・印刷確認・組み立て）に、故障前の注文が出ている | |
| 2 | 呼び出しモニターに、`ready` の番号が出ている | |
| 3 | 注文状況ページ（`/orders/<ID>`）で、画像が表示される | |
| 4 | 新しい注文が、故障前の最後の注文番号の**次**の番号で採番される | |
| 5 | `printing` のまま残っていたシートが、印刷確認の画面に出る（印刷係が、紙を見て確認する） | |
| 6 | `check-backup.ps1` が `OK` | |

### 失われるもの

- **最大でバックアップの間隔（既定 5 分）の分の注文・操作**。バックアップのあとで入った注文は、復旧後の DB にはない。来場者の画面は、その注文が見つからなくなる。**スタッフは、直前の注文を持つ来場者に、もう一度注文してもらう**（紙で控えている番号があれば、手で対応する）
- 復旧のあと、`printing` のシートは、実際に紙が出たかどうかを、印刷係が確認する

## 別に保管するもの

バックアップに入らない秘密情報は、**処理PC とは別の安全な場所**（管理者のパスワード管理ツール、鍵のかかる場所の USB メモリなど）に保管する。予備機を作るときに必要になる。

- `.env` の中身（特に `CF_ACCESS_AUD`・`TURNSTILE_SECRET_KEY`。**チャットやメールに貼らない**）
- `%USERPROFILE%\.cloudflared\` の `config.yml`・`<トンネルID>.json`・`cert.pem`
- 専用ユーザー `canbadge` のパスワード（自動ログオンの再設定に使う）

なくした場合：Cloudflare のダッシュボードで、トンネルの作り直し・Access・Turnstile のキーの再発行ができる。ただし、時間がかかる（学祭当日には間に合わない）。

## 4. 復旧のリハーサル

**リハーサルは、必ず実施する**（spec.md 14 章）。学祭の 1〜2 週間前までに、**予備機**で、上の復旧手順を通しで行う。

記録する：

| 項目 | 記録 |
| --- | --- |
| 実施日・実施者 | |
| 使った予備機 | |
| 手順 1〜7 に、かかった時間（目標：1 時間以内） | |
| 詰まった点・手順書の直し | |
| 確認の 1〜6 の結果 | |
| データの食い違い（注文の件数が、本番と一致するか） | |

リハーサルでは、本番の処理PC のバックアップ（本物でも、サンプルデータでもよい）を使う。**本番の処理PC には触らない**。

## 開発・手元での操作

```sh
bun run backup                                   # .env の BACKUP_DIR に、バックアップを 1 回取る
bun run restore <バックアップの置き場所> [--force]  # 復旧する（api を止めてから）
```

- 同じ 1 秒以内に 2 回取ろうとすると、名前が重なって失敗する（定期実行では起きない）
- 復旧先を変えるときは、`DATA_DIR` を指定する（予備の場所で試せる）
